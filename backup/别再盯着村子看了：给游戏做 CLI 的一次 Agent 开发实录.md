最近在折腾一件有点绕的事：让 Agent 帮我给《怪物猎人：崛起》做一个肉鸽模式。

大致设想是，在斗技场里一波一波打怪，清波拿 PT，再买药、买增益、抽装备，继续下一层。听起来像改几个数值，实际做起来，从同场续怪到结算返回，每一步都要接上游戏自己的逻辑。

这次让我印象最深的进展，是给这款没有现成开发命令行的游戏，补了一条我们自己的 CLI。

但我写 CLI 的最初动力，说出来其实没这么体面：

**GPT 的 Computer Use 连 WASD 都不会，能让游戏卡在那里一晚上。**

我需要它进任务、移动角色、去怪物旁边做实验。它却可能连最基本的移动都折腾不明白，让游戏开着，卡在同一个场景里耗上一晚上。我不想一直守在电脑前，替它完成这些基础操作。

所以才决定自己写 CLI，把进入任务、移动到目标、读取状态和执行实验这些步骤做成它能直接调用的命令。

后来才逐渐发现，这条 CLI 还让测试、状态核对和证据留存变得更可靠。最直接的感受是，我终于不用一直在旁边提醒：你现在在哪、刚才点到了什么、到底有没有成功。

## 先别研究传送，先进任务

前期的合作方式很朴素：Agent 看截图、找按钮、操作 REFramework 的面板，再读日志判断发生了什么。

这套方法当然能做事，也很容易磨人。

它会把斗技场起点认成村庄，在任务里尝试重新接任务；也会待在村庄里研究“回营地”，忘了先进入一个真正存在营地的任务。我一度觉得自己请了一个很喜欢欣赏村子风景的助手。

结算界面也是如此。人坐在电脑前，连续按几下确认键就过去了，Agent 却可能反复截屏、判断焦点、等画面变化。忙了半天，实验还没有开始。

后来我越来越明确地要求：能用 CLI 就用 CLI，Computer Use 留给画面确认。

研究游戏机制需要反复进入相同现场。一次偶然点成功，离可复现的实验还有很远。

## 给游戏补上可调用的操作

我们的工具链通过 REFramework 接入运行时，再用原生插件、HTTP 桥接和 Node.js CLI，把一部分操作暴露出来。另一条 Agent 工作线还补上了通过 HTTP 重载脚本、执行指定 Lua 脚本的能力。

于是，实验可以写成这样的命令：

```powershell
node cli/mhr.mjs doctor --json
node cli/mhr.mjs state --json
node cli/mhr.mjs game reset --json
node cli/mhr.mjs game run-script probe.lua --json
```

进入战斗以后，也有明确的业务操作：

```powershell
node cli/mhr.mjs test invincible on --json
node cli/mhr.mjs wait --stage Combat --timeout 45 --json
node cli/mhr.mjs test tp --to monster --json
node cli/mhr.mjs shop buy --item buff_atk --json
```

这些是项目自己的命令，需要配套插件和脚本运行。它们把“点界面上的某个位置”变成了“请求执行一个有名称、有参数的操作”。

结构化状态里可以带上阶段、任务实例、波次 token、怪物 UID、PT 和商店资格。命令也能携带身份信息，拒绝旧会话的请求。脚本重载、任务切换以后，Agent 有了重新核对现场的依据。

更实际的变化是，Agent 可以自己完成一次循环：发命令、等阶段、采样、保存 JSON、对比结果。失败时，我也有机会看到它具体失败在哪一步。

## CLI 也会说半句话

命令行很容易给人一种可靠感，但这次也遇到了“命令的成功”和“事情的成功”对不上的情况。

例如 `kill-all`：请求已经排进队列，怪也确实死了，CLI 却因为没有收到最终回执而超时。

如果只看退出码，Agent 会认为击杀失败；如果只看 `queued`，又可能把受理当成完成。此时再执行一次，还可能误杀刚刷出来的下一只。

所以，异步操作需要把受理、执行完成、拒绝和结果不明分开表达。等待应该有具体条件，执行之后也要重新读取真实状态。

另一个坑来自探针。同一轮脚本会话里，反复执行同名脚本，CLI 可能拿到上一份已经发布的报告。后来这轮采样改用唯一脚本名，避免把旧结果算作新证据。

这种问题提醒我：给 Agent 做工具，还要设计好它能观察到什么。一个模糊的“成功”，可能比明确的失败更费时间。

## 从猜状态到追原生调用链

游戏机制的研究也经历过类似转折。

我们最初尝试复活旧怪：改状态、调用 `repop()`、清销毁标记，再等它出现。几轮实验都没有结果。

后面结合元数据、原生函数反汇编和运行时追踪，才发现此前盯着的一个复活更新函数处理的是小怪列表。首领出场走另一套任务状态机，两只预设首领出完以后，调度已经结束。

方法名看起来相关，并不能证明它负责我们要改的对象。

之后改走首领的原生登记、加载和创建流程，才在同一个任务里追加出了新怪。接着逐项验证：换怪种、讨伐、清理、复用槽位、全灭后续波。

CLI 在这里提供了一种很有用的约束：每次操作前后都能记录任务身份和怪物 UID。“怪又出来了”可以继续追问：是旧对象复活，还是一个新的对象？新对象死后，游戏有没有登记？下一轮还能不能重复？

这些问题很难靠一张截图回答。

## 让数值来验收 buff

最近一轮工作是修复商店增益和恢复机制，再验证重复购买。

原实现已经有 191 条测试通过，复核时仍找出了几个漏洞：恢复记录写盘失败会被当成成功；临时装备清理按型号搜索，可能删错同型号副本；清包部分失败后可能漏掉恢复；“单轮增益”绑定到了整个原生任务；会心公式还依赖上次返回值，相同输入重复读取也可能漂移。

测试可以全部通过，因为测试没有问到这些情况。

修复后，验证顺序变成了：先补故障回归，再构建部署，最后通过 CLI 购买并采样游戏里的真实玩家数据。

这轮角色的基线是攻击 340、防御 75、会心 −25%。三种增益每次分别增加 10、15 和 10 个百分点。

| 攻击／防御／会心购买次数 | 实测攻击 | 实测防御 | 实测会心 |
|---|---:|---:|---:|
| 3／2／3 | 370 | 105 | 5% |
| 1／3／2 | 350 | 120 | −5% |
| 2／2／2 | 360 | 105 | −5% |

此外又在最终部署版本上重复了一组。有效采样报告各有六次观测，数值保持一致。

更关键的是生命周期：准备阶段购买后，数值暂时不变；进入战斗才启用；清波后恢复基线；同一个任务里，下一波没有购买就不会继承。取消购买和战斗中主动停止，也都单独测了。

这比一句“按钮能点，功能已完成”具体得多。

最终回归测试到了 198 条。实机收尾还核对了原装备、背包、临时防具数量，并恢复测试配置、关闭无敌、回到村庄。测试本身也要有结束状态。

过程中仍然发现了独立的出怪时序问题：肉鸽层数已经推进，上一只怪的原生死亡状态却还没完全落稳，过早选择下一波会失败。它被保留为待办，没有因为 buff 实测通过就一起算成解决。

做完这一轮，我会更愿意先花时间给 Agent 准备一条好用的 CLI。

画面依然有用：怪物外观是否异常、UI 是否遮挡、角色到底站在哪里，都值得看一眼。但需要重复执行的操作、可以直接读取的状态，以及最后用来判断成败的证据，尽量交给可编排的接口。

Agent 还是会犯错。现在它更容易把错误留在一个能够定位、能够复测的地方，我也更容易判断它到底有没有往前走。
